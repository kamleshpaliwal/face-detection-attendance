Face Attendance Enterprise

A school attendance system. A student registers once with a face photo, and later a camera scan marks them present. This page covers what was built, why, and how, then a plan to make it production ready.

Browser camera→FastAPI→DeepFace Facenet512→Milvus search→MySQL record
FrontendStatic HTML: register.html, attendance.html
APIFastAPI + Uvicorn, Python 3.11
Face AIDeepFace, Facenet512, OpenCV detector, 512-dim vectors
Relational DBMySQL 8 via SQLAlchemy
Vector DBMilvus 2.4, HNSW index, cosine metric
Admin UIAttu, the Milvus browser, on port 8001
Git holds only two commits, so these steps are reconstructed from the code in logical build order, not from commit history. milvus/ and server/.dockerignore are still uncommitted.

What was built, step by step

Step 0

Problem and design decisions

What
Register a face once, then mark attendance automatically from a camera scan.
Why
  • Python/DeepFace replaces browser-side face-api.js (128-dim). It is more accurate, and the client can't tamper with embeddings.
  • MySQL suits relational data and uniqueness rules.
  • Milvus does fast nearest-neighbour search without scanning every row.
  • Docker Compose starts the whole stack with one command.
Step 1

Configuration

config.py
What
A Settings class (pydantic-settings) for DB credentials, Milvus address, model, detector, dimension (512), threshold (0.60), timezone, 8 MB image cap, CORS origins and client directory.
Why
No secrets or environment values in code. The same image runs locally and in Docker.
How
Loads from env vars or server/.env. The password is URL-encoded in the DB URL. .gitignore keeps real .env files out and only .env.example in.
Step 2

Relational layer

database.py · models.py · schemas.py
What
Student (unique studentCode, names, dob, class, section) and Attendance (studentId, date, time, confidence), with Pydantic request and response models.
Why
A unique constraint on (studentId, date) enforces one attendance row per student per day, even under simultaneous scans. pool_pre_ping and pool_recycle avoid stale-connection errors.
How
create_all builds missing tables at startup.
Step 3

Face embedding pipeline

faces.py
What
One function turns an uploaded image into a 512-float vector.
Why
Registration and attendance must produce comparable vectors, and bad input must never reach the model.
How
  1. Allow only JPEG, PNG or WebP (else 415).
  2. Read at most 8 MB (else 413).
  3. Decode with OpenCV (else 400).
  4. Run DeepFace with Facenet512, the opencv detector, enforced detection and alignment.
  5. Require exactly one face.
  6. Check the vector has 512 finite values.
Step 4

Vector layer

vectors.py
What
A Milvus wrapper. The collection student_faces_facenet512 has primary key student_id and a 512-dim embedding with an HNSW index (M=16, efConstruction=200) and the cosine metric.
Why
Keeps similarity search out of MySQL and scales with student count. The model name in the collection name stops old 128-dim vectors being mixed in.
How
put() upserts, so re-registering replaces the vector. nearest() returns the top-1 student and score.
Step 5

API

main.py
What
The endpoints in the table below, plus CORS and static hosting of the client.
Why
  • Startup retries Milvus up to 12 times, because Milvus is slow to start.
  • A nearest neighbour always exists, even for strangers, so the score must pass the threshold.
  • The attendance check plus IntegrityError handling makes marking idempotent.
  • "Today" uses the configured timezone, matching the school's day.
Step 6

Frontend

register.html · attendance.html
What
A registration form with camera capture, and a scan page that sends a frame every 2 seconds.
Why
No build step. The browser only sends images, so all recognition logic stays on the server.
How
getUserMedia gives the stream. A canvas turns a frame into a JPEG blob, uploaded as multipart field image on the same origin.
Step 7

Containers

Dockerfile · docker-compose.yml
What
Four services: mysql, milvus, attu and app. The Dockerfile uses python:3.11-slim with the OpenCV system libraries.
Why
Milvus runs standalone with embedded etcd and local storage, so there are 3 infrastructure containers instead of 5. Healthchecks make startup order reliable, and a cache volume keeps model weights between restarts.
How
app waits for healthy MySQL and Milvus. Compose fails fast if MYSQL_ROOT_PASSWORD is unset.
Step 8

Latest uncommitted changes

What
The modified docker-compose.yml (embedded etcd), plus the new milvus/embedEtcd.yaml and server/.dockerignore.
Action
Commit them. A fresh clone can't start Milvus without them.

Production readiness plan

Priority: P0 blocker before real users, P1 needed soon after, P2 improvement.

Phase 1: Security and privacy P0

#TaskWhy and how
1.1Authentication and rolesAnyone can register students or mark attendance today. Use JWT or OAuth2 with admin, teacher and kiosk roles. A kiosk gets a scoped key for /attendance/mark only.
1.2HTTPSCamera access needs HTTPS outside localhost. Put Caddy, Nginx or Traefik in front and don't publish port 8000.
1.3Close infrastructure ports3306, 19530, 9091 and Attu are exposed. Remove the ports entries and protect Attu.
1.4Dedicated DB userThe app connects as root. Create a least-privilege user.
1.5Secrets managementDocker secrets, Vault or a cloud secret manager instead of .env files.
1.6Anti-spoofingA printed photo can mark someone present. Use DeepFace anti_spoofing or blink and head-turn challenges, and test with real attempts.
1.7Biometric complianceConsent capture, access audit log, retention policy, and a delete endpoint that clears MySQL and Milvus together. Check local law (for example DPDP, GDPR).
1.8Rate limitingEach scan is expensive. Use slowapi or proxy-level limits.

Phase 2: Correctness and accuracy P0P1

#TaskWhy and how
2.1Calibrate the threshold0.60 is a demo value. Build a labeled validation set, plot false accept and false reject rates, and choose to fit the school's risk tolerance.
2.2Stronger detectorThe opencv (Haar) detector is weak with angles and light. Benchmark retinaface, mtcnn and yolov8.
2.3Several embeddings per studentOne photo is fragile. Store 3 to 5 and match on the best score. This needs an auto ID primary key in Milvus.
2.4Ambiguity marginTake the top 2 matches and reject the scan if the gap is too small.
2.5Consistent stateMySQL and Milvus are written separately. Add a reconciliation job and ordered deletes.
2.6Bug and cleanup fixesReplace deprecated datetime.utcnow, create the Milvus client in lifespan instead of at import, and adopt Alembic instead of create_all.
2.7Consistent status codes/attendance/mark returns 200 with success:false for "not recognized". Use proper codes and an error schema.

Phase 3: Features P1

  • Attendance read APIs by date, class and student, with daily and monthly summaries and CSV or Excel export.
  • Student update, delete and soft-delete, face re-enrollment and bulk CSV import.
  • Manual teacher override with a reason and audit trail.
  • Late and absent logic using school hours and per-class schedules.
  • Admin dashboard with login, and pagination and search on /students.
  • Parent notifications (SMS, email or WhatsApp) for absences.

Phase 4: Performance and scalability P1

  • Warm up the model at startup. The first request currently takes minutes.
  • Run DeepFace in a thread or process pool. It currently blocks the async event loop.
  • Run multiple workers, and consider GPU inference if volume needs it.
  • On the client: skip frames with no face, throttle polling, and resize images before upload.
  • Use a real Milvus deployment and backed-up or managed MySQL. Embedded etcd and local storage suit development only.

Phase 5: Reliability and operations P1

  • Backups: scheduled MySQL dumps and Milvus snapshots, with a tested restore.
  • Logging: structured JSON logs with request IDs. Never log images or embeddings.
  • Monitoring: Prometheus and Grafana for latency, match rate and errors. Extend /api/health to check MySQL and Milvus.
  • Containers: non-root user, pinned base images, Trivy scans, resource limits and restart policies.

Phase 6: Quality and delivery P1P2

  • Tests: pytest unit tests, API tests with DeepFace and Milvus mocked, Compose integration tests, and a regression set of face images.
  • CI/CD: GitHub Actions running ruff, mypy, tests, image build and scan, then deploy.
  • Migrations and config: versioned Alembic migrations and separate dev, staging and prod configs.
  • Dependencies: a lock file. deepface>=0.0.93 has no upper bound.
  • Docs: OpenAPI examples, a runbook and deployment notes.

Definition of production ready

  • All endpoints authenticated, and traffic over HTTPS only
  • No database or vector ports exposed publicly
  • Threshold calibrated on real data, with measured false accept and false reject rates
  • Anti-spoofing enabled
  • Consent record and a deletion path for biometric data
  • Backups run and the restore has been tested
  • Monitoring and alerts in place
  • Automated tests and a passing CI pipeline
  • Pilot completed with real users
